# Repeat-dispatch review: duplicate ack re-executes a started task (e772344)

- Status: **DEFECT REPRODUCED at the HostedSupervisor level** (P0, task-duplication). Candidate remains UNAPPROVED. No product edits; no full suites rerun (targeted repro only). Original reports unchanged.
- Lead's provider-level probe (startControlled twice on the same vm after child exit accepted, `spawned_count 2`) is real provider reuse but, as the lead noted, not by itself a task-duplication defect. This review proves the supervisor-level defect the lead asked for: a second `ackAndStart` for the SAME task/lease/fence, after the first child exited and BEFORE any settlement, starts a second physical child.
- Targeted repro (pinned Bun 1.4.2, exact `e772344` scratch `/tmp/sf-frun`; REAL Coordinator + Store + HostedStore + ControlledProcessProvider + actual child; TRANSPORT MOCK ONLY — loopback `Bun.serve` ack fixture replaying the same current lease/fence, modelling lost-ACK retry / duplicate claim delivery; controlled_duration 300 ms):
  - `claimOnce` → `ackAndStart` → `spawned = 1` → sleep 900 ms (first child exits naturally) → mapping state `stopped`, `child_pid` set → second `ackAndStart(same task/lease/fence)` → **ACCEPTED, `spawned = 2`**.
  - Verbatim output: `first ackAndStart done; spawned = 1` / `mapping state before dup ack: stopped | child_pid: 14969` / `SECOND ackAndStart ACCEPTED (re-executed?)` / `spawned count after dup ack: 2` / `RESULT: DOUBLE PHYSICAL EXECUTION`.
- Missing state guard (source refs on e772344 `src/hosted-supervisor.ts`): `ackAndStart` (`126-~310`) never inspects the durable mapping state or `child_pid` before staging/starting — after the ack reply checks (`173-189`) it proceeds unconditionally to `store.create` (idempotent request_id, so no error), pause, `startControlled`. `claimMapping` reuse only dedupes the ROW (same lease/fence returns existing mapping); it does not gate execution. `updateLease(task,{lease,fence},"running")` (line ~300) enforces fence/lease equality but any state may transition to `running` — including `stopped`. `recover()` holds non-settled rows, but nothing in the live path refuses `ackAndStart` on a `running`/`stopped`/pid-bearing row. Note the repro's pre-dup state was `stopped` because the watchdog path is timer-driven and no `stopAndConfirm` had run — a lost-ACK duplicate arriving in exactly this window re-executes.
- Why the prior "duplicate delivery reuses mapping" test does NOT establish physical dedupe: it asserts `claimMapping` row reuse (`created:false`) and same local pointer — a storage-level property. It never calls `ackAndStart` twice and never counts physical spawns. Row dedupe ≠ execution dedupe; this repro counts `spawnedCommands` (1→2) with real children.
- Required fix (author): gate `ackAndStart` on the durable row BEFORE any staging/spawn — e.g. refuse when mapping state is `acknowledged`/`running`/`stop_intended`/`stopped`/`settled`, or when `child_pid`/`runtime_started_at_mono_ms` is already set for this (lease,fence), unless an explicit trusted-retry path first proves OS stop via `stopPidWithProof` and advances the fence/epoch. Regression: exactly this repro (duplicate ack same lease/fence pre-settlement → refusal + `spawned==1`), plus the fence-advanced legitimate-retry case still working after proven stop.
- Scope: this defect is independent of D1–D4 and R1; it compounds R1/P0 (second execution also mints a second pid while the first row's pid record is stale). Server-side idempotency (same-key replay) does not save the local side — the duplicate spawn happens before any settlement. Joint D1 bridge must additionally guarantee the server never re-issues live work for a lease it already acked without a fence advance, but the local guard is required regardless (untrusted/duplicate transport must never start a second runtime).
