## Disagreement 1: settle CAS-miss — LEAD CONFIRMED, B REFUTED (with qualification)

B's theory: "D1 batch rolls back automatically if a conditional UPDATE matches 0, so a CAS miss aborts with zero changes." B's test changed the allowance BEFORE the settle pre-read, so its 409 came from the preflight `reserved_quantity < reservedQty` check — not from a CAS miss. That half of B's critique of their own test is correct.

But B's general claim is FALSE for this code, proven by a REAL D1 forced interleaving (not Bun SQLite):

- Setup: Miniflare D1 fixture + running task (10k runtime, reservation qty 10000, controlled allowance reserved 10000/consumed 0) + live supervisor credential. Called production `hostedDispatchRoute` settle DIRECTLY in Node with a `ctx.env.DB` facade: `prepare` bound to real D1, `batch` applying a REAL `UPDATE hosted_allowances SET reserved_quantity='9000'` exactly once at batch entry (after all pre-reads), then the real batch. All auth/pre-reads hit actual D1; injection lands after reads.
- Result (raw JSON preserved in `disagreement-cas-raw.json`): HTTP **200**, task **completed**, reservation **consumed** (`quantity 10000, consumed_quantity 100, consumed_runtime_ms 100`), ledger **`reserved_quantity 9000 / consumed_quantity 0`** — the terminal state landed while the ledger CAS silently missed. No failing SQL statement, no rollback, no 409.
- Why: D1 `batch()` is NOT an all-or-nothing transaction over conditional statements. Each statement is an independent conditional write; a `WHERE`-missed UPDATE is a *successful* statement that changes 0 rows. The code's only post-batch check is `current.state !== outcomeState` on the final SELECT — the ledger statement's `meta.changes` is never inspected. Task UPDATE matched (lease/fence current, authorizer live), reservation UPDATE matched (task now completed), outbox/audit matched; only the allowance UPDATE missed. Partial terminal state persisted with ledger drift (9000 stuck reserved, 0 consumed).
- Lead's Bun SQLite repro (200/completed/reservation 100/ledger 9000/0) is therefore the faithful model of production behavior, not an artifact of `sqlite.transaction` vs D1. The "atomic transaction fact ≠ zero-changes abort" distinction in the dispatch is sustained: atomicity of *failure* (a thrown statement aborts the batch) does not imply atomicity of *conditional misses*.
- Required fix direction (author, not certified here): check per-statement `meta.changes` for the ledger (and reservation) writes post-batch and convert a miss into 409 with compensating handling, or restructure so the ledger CAS result gates the terminal read (e.g. final SELECT joining ledger expectations). B's serial test does not exercise this path.

WHERE reservation_id=? AND task_id=? AND state IN (…) AND EXISTS(task state=?)`) and the ledger UPDATE (allowance+tenant match only) do not themselves recheck the authorizer. In my run the authorizer was live so all matched; but if authority is lost after the pre-read, the task UPDATE correctly misses while reservation/ledger/outbox/audit statements are evaluated against the *post-batch* task state read… in the observed run the final SELECT gates on terminal state so a full miss still 409s. ## Disagreement 2: authorizing_session_id + session-tied tasks — B REFUTED on facts, LEAD RULING SUSTAINED with a carve-out
- B claims "no authorizing_session_id column ANYWHERE in 0003" and "month-long tasks shouldn't tie 12h sessions." Both premises are factually wrong:

Verified by PRAGMA probe: columns include `authorizing_user_id, installation_id, execution_grant_id, authorizing_session_id`.
  - Task runtime ≤ 1h technical ceiling (`CHECK(runtime_ms BETWEEN 1 AND 3600000)`), not month-long. A 12h session comfortably spans any task; no duration argument against session binding exists.
- Contract semantics (frozen protocol + code): account-direct tasks bind the *current* authorizing user (guard checks user/membership/org liveness, NOT session liveness — `taskAuthorizerGuard` account branch takes `authorizing_user_id` only). CLI-grant tasks bind grant+installation epoch/user/window, intentionally independent of the issuer session (grant survives issuer logout — by design: `authorization_expires_at` mirrors the installation window, not the session TTL).
- Probes: (a) account task seeded WITH a live `authorizing_session_id`, then ALL user sessions revoked (user stays active): claim returns 200 with `{task: null}` — no grant of work, correct fail-closed read of the candidate election (authorizer-user check is what matters; session revocation did not falsely authorize). (b) session revocation does NOT kill the user's own sf-scoped grant path: supervisor credential (separate audience/table) still claims (200) — "user-own sfscoped grant unaffected by issuer logout" confirmed correct.
- Policy continuous-renew: shared protocol rechecks authority at claim/ack/renew/settle and revocation takes explicit effect. Lead ruling sustained: deny new claim/ACK/renew after policy revoke/expiry (pinned guard fails), while cleanup-mode settle with a valid credential still settles (code: `mode === 'cleanup'` path tolerates authorizer/worker/policy loss, requires task/fence ownership). My probes did not contradict this; revocation tests in the candidate suite cover the deny side.
