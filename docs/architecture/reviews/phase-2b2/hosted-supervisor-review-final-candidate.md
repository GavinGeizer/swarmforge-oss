## Finding (1): CONFIRMED, HIGH — `runtime_mono_origin` literal survives restart, so a new process treats a foreign clock as same

- Mechanism (source fact): `markRuntimeStarted` persists `monoOrigin:"spawn-process"`; `fromRow` returns the literal unchanged (hosted-store.ts:666 area); no constructor/process check invalidates a foreign origin. `stopAndConfirm`'s measured path guards on the LITERAL (`mapping.runtime_mono_origin !== "spawn-process"`, :578-581) — which is TRUE for a restarted row — then subtracts the new process's `performance.now()` from the dead process's `performance.now()` (:587-590), and `markStopped`'s origin check (`elapsed.monoOrigin !== current.runtime_mono_origin`, :396-402) compares two `"spawn-process"` literals and passes.
- Concrete evidence (real two-process probe, on-disk DB, actual 60 s child): phase A (process 1) journaled `{mono:125.25, origin:"spawn-process"}`; phase B (process 2, NEW clock) reads the same row — `newProcessNow=37.65` vs `persistedMono=125.25`. A same-process subtraction would already be negative/garbage; across a real restart the origins are unrelated. The author's D2 test only hand-seeds `monoOrigin:"unknown"` (never a production `"spawn-process"` row reopened in a new process), so it exercises the rejection path without proving the production path takes it.
- Why this is reachable, not theoretical: when the canonical Store row EXISTS in the new process (production shares the on-disk Store DB, or the row is re-created), the `:484 canonical-missing` hold branch is skipped and execution falls to the `:578` literal check → passes → garbage `elapsed` → `min(bound)` clamp masks it as plausible consumption. ## Finding (2): CONFIRMED, HIGH — `settle()` persists nothing before HTTP; lost COMPLETED reply + restart recomputes and flips outcome under the SAME key

- Mechanism (source fact, verified by offset probe): `settle()` (hosted-supervisor.ts:639-676) computes `key`, awaits `client.settle(...)` (:652), and only AFTER success calls `rememberIdempotentResponse` (:663) + `markSettled` (:674). No durable `(outcome, consumed, fingerprint)` write precedes the HTTP call. `reconcile()` defaults `settleOutcome:"cancelled"` (:712-714) and `runHosted` calls `recover()` (marks stopped rows held) then `reconcile(cancelled)`.
- Consequence (code-path certain, no timing speculation): COMPLETED task, settlement HTTP succeeds server-side but reply lost (crash/timeout) → restart → row is `stopped` (or held) with `stop_confirmed=true`, `settlement_key` set → `reconcile()` settles it as `cancelled` with the SAME key → server sees same key + changed fingerprint (`lease:fence:cancelled` vs `completed`) → 409 forever, and the true outcome is unrecoverable (neither the outcome nor the consumed payload was journaled pre-HTTP). The fingerprint binds outcome precisely so the flip is a hard conflict, not a benign replay.
- Required: persist `(outcome, consumed_runtime_ms, settlement_key, fingerprint)` durably BEFORE the settle HTTP (new column/state, e.g. `settle_intended`), and make `reconcile()` reuse the persisted outcome/key instead of defaulting to `cancelled`. Regression: lost-reply simulation (settle HTTP succeeds, caller crashes before persist) + new-process reconcile asserting the EXACT original payload/key (completed + measured consumption), not a recomputed cancelled.

## Finding (3): CONFIRMED, MEDIUM-HIGH — verified-dead runtime that lands in `heldUnknown` can never release

## Finding (4): CONFIRMED with probe — compile detection should prefer `Bun.isStandaloneExecutable` over the ENTRY env marker

- Source fact: provider branch selection reads `process.env.SWARMFORGE_HOSTED_ENTRY` (hosted-runtime.ts:175); `isStandaloneExecutable` appears nowhere in `src/` or `scripts/`.
- Probe (official Bun 1.4.2, installed docs build 858 semantics): dev `bun` → `isStandaloneExecutable === false`; compiled probe binary (`--compile --target=bun-linux-x64-baseline`) → `true`, with `execPath` = the binary itself. The API exists and discriminates exactly the right condition (am-I-the-shipped-binary vs am-I-a-bare-runtime), whereas the env marker is caller-controlled ambient state that any parent process, test harness, or attacker can set/unset — including launching the binary WITHOUT the marker (falls into the dev `.ts`-script path inside a compiled binary where `$bunfs`/repo files don't exist) or setting it under dev `bun` (takes the self-spawn path without a bundled entrypoint).
