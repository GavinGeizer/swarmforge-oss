## 1. Evidence (source-grounded)

### 1.1 Repository / GitHub / model secret handoff into the worker
- Three push modes in `src/config.ts:58-60`: `none | github-app | github-oauth | ssh`, with per-mode required fields (`src/config.ts:134-190`).
- `src/providers/freestyle.ts:241-303` (`withGitAuth`): writes the credential into the guest at `/opt/swarmforge/git-secret` (mode 0600) plus an ASKPASS/SSH wrapper, runs clone/push, then `rm -f` both paths and throws if cleanup is unverified. Failure to clean is fatal, but a compromised guest process can copy the secret before cleanup — the docs already concede this (`identity-and-trust.md:58`: "Do not reuse the current temporary-file mechanism as proof of cloud isolation: a compromised process can copy a credential before cleanup").
- `github-oauth` mode: Device Flow requests broad `scope: "repo"` (`src/github-oauth.ts:165`); the **user's** token enters the guest (`freestyle.ts:256-260` via `githubOauthToken`). Scope is GitHub-side broad; binding to one repository is local policy only (`githubOauthToken` repository check, `src/github-oauth.ts:84-95`).
- `github-app` mode: `src/git-handoff.ts:17-75` mints an installation token with `repositories: [<one repo>]`, `permissions: {contents: write}`. Still repository-wide, not branch- or task-scoped.
- `ssh` mode: copies the raw private key + known-hosts into the guest (`freestyle.ts:271-284`).
- Model key: `workerEnvironment` (`src/config.ts:248-261`) injects `SWARMFORGE_MODEL_API_KEY` into **every** worker; `src/providers/opencode.ts:16-36` writes an opencode config referencing `{env:SWARMFORGE_MODEL_API_KEY}` into the guest, and per-worker Basic `opencode:<server_password>` guards coordinator-to-runtime access (`opencode.ts:71-88`). `server_password` (128-bit random per worker, `src/store.ts:277`) is stored in SQLite workers body.
- Coordinator holds `FREESTYLE_API_TOKEN` (provider management authority) process-side only; it is never written into the guest (no reference in `workerEnvironment` or `prepare`).

### 1.2 Worker identity client and credential files — what exists
- **No worker enrollment client exists in `src/`.** There is a CLI client only:
  - `src/cloud-client.ts` (`CloudClient`): link `start` (256-bit proof, `randomBytes(32)`), `cancel`, `exchange` (poll loop, 429/backoff, strict URL/expiry validation), `me`, `organizations` (cursor loop, cycle-guarded), `revoke`, `rotate` (fresh idempotency key per call). Bounded: 30 s timeout, 128 KiB body cap, `redirect: "error"`, `credentials: "omit"`, exact-origin `cloudOrigin`.
  - `src/cloud-credentials.ts`: `cloud-credentials.json`, schema version 1, `sfcli_` format, `0600` file / `0700` dir, `O_NOFOLLOW`, ownership/nlink checks, exclusive temp + fsync + atomic rename. **POSIX-only**: throws without `process.getuid` ("use a supported Linux or macOS host"); Windows explicitly unsupported.
  - `src/cli/cloud.ts`: `login/use/status/logout/organizations/rotate`; origin pinning; failed-save triggers server revoke (no orphan grant); ambiguous logout exit codes surface unconfirmed revocation.
- Server side (implemented, `apps/cloud/src/machines.ts`, `enrollment.ts`, `links.ts`, `connect.ts`, `index.ts` route table ~lines 378-487): CLI audience `cloud-cli` (`identity:read`, `devices:self`, 24 h TTL) and worker audience `worker-identity` (`worker:identity`, `worker:rotate`, 1 h TTL), 30-day authorization grants, epoch CAS rotation with 10-minute exact-context rotation replay, single-use enrollment (`sfenroll_`, 10 min, owner/admin-gated, 25 pending / 100 workers per tenant caps). Worker endpoints that **do** exist: `POST /v1/workers/register`, `GET/POST /v1/workers/me`, `/v1/workers/me/rotate`, tenant `worker-enrollments`/`workers` CRUD. `machineAuth` never falls through to cookie/instance/GitHub bearers; every request rechecks membership/epoch/expiry/revocation; `last_seen_at` is throttled metadata, never authority.
- Credential files at rest: `github-oauth.json` (0600, `src/github-oauth.ts:39-66`), `cloud-credentials.json` (above), SQLite `credential_screening` + `workers.body.server_password` (`src/store.ts:48-97`), DB file 0600 + WAL. Known committed risk: raw OAuth token copies persist in SQLite; credential-file logout does not erase them (Phase 1 risk register; `identity-and-trust.md:66`).
- **Missing**: no `src/worker-credentials.ts`, no `src/worker-identity-client.ts`, no worker daemon (rotation loop, revocation recovery, reconnect), no heartbeat/lease/assignment/task/dispatch/usage/entitlement route anywhere in `apps/cloud/src` (grep for heartbeat|lease|assignment|dispatch|reservation|entitlement: no hits). Phase 2B.1 summary states explicitly: "Worker enrollment creates identity metadata only; no VM, heartbeat, task, repository broker, dispatch, inference, usage or billing endpoint exists."

### 1.3 Leakage surfaces (logs / prompts / artifacts / snapshots)
- Redaction is real but documented as **not a boundary**: `src/security.ts` (`Redactor`: exact + URL-encoded + base64 variants, `sfcli_|sfworker_|sfenroll_` regex, URL-password and `?token=[REDACTED] scrubbing, key-name screening of `authorization|credential|api_key|password|secret|token`); `src/settings/inspect.ts` (SECRET_KEYS, context redaction, control-char stripping, order: redact→plain→redact so cleanup cannot reassemble a secret); coordinator excerpts (`excerptText`, redact-before-truncate), finalization errors (redact-before-truncate), MCP diagnostics (machine-format redaction even for never-loaded accounts), `redactedSettings`/`redactedText` CLI surfaces, route-template-only cloud logs with `no-store`, trace redaction, invocation logs disabled.
- Admitted gaps: arbitrary echoed App tokens/SSH material "not demonstrated screened"; OAuth token copies in DB; base64/URL variants of *unknown-to-this-process* secrets are not caught except by the three machine-format regexes; a workspace snapshot tarball (`artifact-transport.ts`/`artifact-helper.py`) captures whatever the worker wrote — `screeningWindow` refuses reads when a configured secret is wider than the window, but that is a read guard, not workspace hygiene. Prompts sent to the model contain task text verbatim; nothing prevents a task author from pasting a secret into a prompt except review.

## 2. Inference (what the evidence entails)
- **Brokered narrow repository operations are NOT complete now.** There is no broker endpoint, no per-task token minting service, no ref/operation policy gateway, and no worker-side consumer for scoped credentials. The only repo-capable paths are the three broad self-hosted modes. Installation tokens are single-repo but still `contents:write` across all branches.
- **A worker enrollment client is the correct next slice**: server APIs (`register/me/rotate`) are implemented and tested (52 cloud tests incl. real CLI/workerd bridge per Phase 2B.1 summary); the local counterpart is absent. This is a bounded client+storage task, not a protocol redesign.
- **Rotation/lease math already constrains the client design**: 1 h worker TTL implies rotate-by ~30 min; rotation is epoch-CAS with same-key replay only; heartbeats/leases do not exist, so "reconnection" today means re-authenticate + epoch check, and any future heartbeat must be a new audience-scoped protocol, never an extension of `worker:identity` into execution authority.
- **Redaction must not be cited as isolation** in any hosted-lane proposal; the repo's own docs forbid it. Isolation has to come from *not handing the secret to the guest at all* (broker) plus distinct audiences, short TTLs, epoch revocation, and network/compute sandboxing that this investigation did not find in source.

## 3. Recommendations

### 3.1 Minimal worker enrollment client (concrete interfaces)
New files (mirror, do not generalize, the CLI pair):
- `src/worker-credentials.ts` — `workerCredentialSchema` (version 1, `credential: /^sfworker_[A-Za-z0-9_-]{43}$/`, `worker_id/subject_id/tenant_id` UUIDs, `scopes` exact tuple `["worker:identity","worker:rotate"]`, `expires_at ≤ authorization_expires_at`); `workerCredentialPath()` default `<configdir>/worker-credentials.json` overridable by `SWARMFORGE_WORKER_CREDENTIALS_PATH`; identical POSIX storage primitives (0600/0700, no-follow, nlink==1, ≤16 KiB, atomic rename+fsync). POSIX-only like the CLI file — consistent with Linux-glibc-only release scope.
- `src/worker-identity-client.ts` — `class WorkerIdentityClient { register(enrollmentId, enrollmentSecret, runtime_version, capabilities): Promise<...> (single-use; user-code-style confirmation not needed — secret possession IS the proof); me(); rotate(); }` with: strict Zod parsing of every response; exact-origin check; 30 s timeout; `redirect:"error"`; `credentials:"omit"`; bounded retries — retry only `429` (honor `Retry-After`, clamp 5–120 s) and `5xx`/network, max 3 attempts exponential backoff with jitter, idempotency-key **reused across retry attempts of the same logical rotation** (required for rotation-replay recovery), fresh key per logical operation; rotation scheduled at 50% TTL with one early retry at 75%; on `401`/epoch mismatch → stop, delete local file, require fresh invitation (never loop re-register with a consumed secret).
- Worker daemon behavior: outbound-only HTTPS; reconnect = `me()` → verify `worker_id/tenant_id/registration_epoch` match stored identity, else halt; revocation recovery is fatal-by-design (exit nonzero, operator re-enrolls). The worker process must never receive `FREESTYLE_API_TOKEN`, GitHub tokens/keys, model keys, or other tenants' material; model access for hosted workers arrives only via a future tenant-bound proxy (not in this slice).
- Tests (exact): `tests/worker-identity-client.test.ts` — private-file permission/ownership/symlink rejection; malformed-response rejection; audience confusion (`sfcli_` rejected, cookie rejected); rotation success + same-key replay after simulated drop; concurrent-rotation conflict handling; revoked-epoch halt + file deletion; retry budget (no retry on 400/401/403/404/409, bounded retry on 429/503); origin-mismatch refusal. Server contract tests already cover the other half; add a real-client/workerd bridge test mirroring the CLI one.

### 3.2 Controlled-test hosted lane without exposing broad runtime credentials
- **Never** point a hosted-lane test at production `FREESTYLE_API_TOKEN`, production model keys, real GitHub App keys, or the real OAuth credential file. Provision dedicated throwaway credentials (separate Freestyle token, separate model key with spend cap, ephemeral test repo + throwaway GitHub identity) and run the lane against local workerd/D1 or an isolated preview database only.
- Lane shape: coordinator configured with `SWARMFORGE_GIT_TREE=none:<test-tree>` + `SWARMFORGE_GIT_PUSH_MODE=none` (no clone, no push, no guest secret write — see `gitTree`/`withGitAuth` early-returns) and a **no-secret worker**: no `SWARMFORGE_MODEL_API_KEY` in scope; the opencode provider call is stubbed or pointed at a local fake. This exercises enrollment→identity→rotation→revocation and (later) lease/heartbeat plumbing with zero broad-credential exposure.
- **Local real linking is possible without printing secrets**: Phase 2B.1 already bridges the real Bun CLI against local workerd/D1; Phase 2A verified real GitHub web sign-in locally. A linker can re-run those flows read-only (row counts, status codes, redacted diagnostics) — but this investigation attempted no live auth and claims none. Secrets must never appear in output: use `redactedSettings`/`redactedText` surfaces, `*_revoked` booleans, and D1 `count(*)` checks.

### 3.3 Enforceable disabled gate (because brokered repo ops are unsafe/incomplete)
Since no broker exists, the gate must make hosted repository work **structurally impossible** while preserving self-hosting:
- Add (future implementation, not this investigation) a config kill-switch, e.g. `SWARMFORGE_HOSTED_DISPATCH_ENABLED` default `false`, where the coordinator refuses any hosted-claim/dispatch path and any guest write of a cloud-tenant-scoped repo credential unless explicitly enabled with a test-only credential set; and keep `worker:identity` audience incapable of authorizing task assignment, repo access, or inference (server-enforced, as today).
- Safe default runtime preserved: local self-hosted modes (`github-app/github-oauth/ssh/none`) unchanged; controlled tests run the no-repository/no-secret shape from §3.2. Gate removal requires, at minimum: repository broker with per-task least-privilege tokens + ref/operation policy enforcement, tenant-bound inference proxy, entitlement reservations, lease/revocation propagation, and adversarial-worker tests — i.e. Phase 2B.2 prerequisites 4–5 from the 2B.1 summary.
- Challenge to lead assumptions: (a) do **not** assume `contents:write` installation tokens are "narrow enough" — they are repo-wide and need a gateway for branch/task policy; (b) do **not** extend `worker:identity` scopes to cover execution — mint a separate heartbeat/lease audience when that protocol is designed; (c) do **not** treat redaction, `last_seen_at` throttling, or audit coverage as compensating controls for credential exposure; (d) POSIX-only storage is acceptable *because* the release scope is Linux glibc, but say so explicitly and keep the hard error (no silent fallback).

## 4. Unknowns / unanswered questions
1. Owner decisions still open (product-tiers): BYOK secret custody, repository broker vs. GitHub App choice, worker sizes/quotas, retention windows — the broker design cannot finalize without the custody decision.
2. Preview reality: no remote preview sign-in, migration, quota/CPU measurement, or abuse-limit validation has run (2B.1 summary §70.1–2). Local workerd evidence does not establish edge CPU fit.
3. Windows: explicitly out of scope; no design exists. OS-vault storage (Linux keyring/macOS Keychain) is future work — file fallback protects only against other-user access, not same-user/root/disk compromise.
4. Whether the model proxy for hosted workers should be per-task credentials or a server-side inference gateway — deferred to the managed-inference phase; this client must not bake in either.
5. Backup/restore semantics for machine grants (revoke-on-restore rule is documented but untested operationally).
