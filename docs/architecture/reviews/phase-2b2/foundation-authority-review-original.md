## Blocking findings

### P0 — Entitlements DTO contract mismatch: route omits `consumed_quantity`, adds unapproved `policy_version`
- Contract (frozen, independently approved): `hostedEntitlementViewSchema` (`hosted-types.ts:78-88`) = `{policy, allowed, denial, reserved_tasks, reserved_reservations, consumed_quantity}` — strict, **no `policy_version`**, **requires `consumed_quantity`** (nullable quantity).
- Route (`hosted-entitlements.ts:359-368` local `entitlementViewSchema`, used at `:426`) = `{policy, allowed, denial, policy_version, reserved_tasks, reserved_reservations}` — **adds `policy_version: number|null` and omits `consumed_quantity`**.
- Dispatch requires: "author interface adds policy_version and omits consumed_quantity: verify contract (don't infer approval from docs)". Verified: the route shape does NOT match `hostedEntitlementViewSchema`/protocol. The protocol doc (`phase-2b2-protocol.md`) describes entitlements as "current policy/denial and reserved/consumed counts" — no `policy_version` in the route contract. `policy_version` inside `AdmissionReply.task.policy_version` is a different (approved) interface and does not authorize a second top-level field.
- Reproduction: any `GET /v1/tenants/{t}/entitlements` response parsed with `hostedEntitlementViewSchema` throws (strict: unrecognized `policy_version` + missing `consumed_quantity`). The candidate's own tests never parse the route output with the frozen schema (they assert ad-hoc field subsets), so the mismatch is uncaught.
- Fix (author): align one side with lead approval — either add `consumed_quantity` (with a defined aggregation over allowances/reservations) and remove `policy_version` from the route view, or get the frozen schema + protocol doc amended first. Do not ship the divergence silently.

### P1 — `currentPolicy` newest-version semantics vs `activePolicyGuard`: revoked/expired newest row can mask an older granting row
- `currentPolicy` (`hosted-entitlements.ts:139-183`) returns `ORDER BY version DESC LIMIT 1` **without** revoked/expiry filtering; `evaluatePolicy` then denies on the newest row. `activePolicyGuard` (`:132-137`) instead checks `EXISTS(... revoked_at IS NULL AND valid_from<=now<valid_until)`.
- Dispatch requires "revoked/expired must not fallback older granting row" — i.e., newest-version-wins must hold in BOTH read and guard paths. Counter-scenario: v2 (newest) revoked → read path denies (correct, no fallback). But `activePolicyGuard` only asserts *some* active row exists — with v1 active + v2 revoked, the guard passes on v1's behalf while the read path reports `policy_revoked/v2`. Today both fail closed for reads (no admission exists yet, "no admission yet" per scope), so no grant is wrongly issued; but the two functions already disagree on "which policy governs," and the first downstream admission batch that composes `activePolicyGuard` without a newest-version predicate will admit under v1 while the API reports v2-revoked. The inconsistency is real and must be resolved before admission lands.
- Fix (author): make the guard newest-version-precise (e.g. `version = (SELECT MAX(version) ...)` + active predicates) or document + test the intended semantics (guard = existence; decision = newest) with an admission-time assertion that the admitted `policy_version` equals the newest version. Add a test with v1-active/v2-revoked asserting guard and decision agree.
