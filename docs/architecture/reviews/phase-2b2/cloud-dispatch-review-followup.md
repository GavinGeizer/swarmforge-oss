- **S1 PARTLY CONFIRMED, downgraded to LOW: ledger-CAS-miss partial state is bounded, not zero.** Settlement batch order is task-terminal (:750/:764) → reservation (:768) → ledger CAS (:700-built, appended :779) → outbox-dead → audit, with the final check only on `current.state === outcomeState`. My R1 LIVE re-verification (metered seed qty 100, drain reserved 100→5, settle 40): **409, task `running`, reservation `active`, ledger `reserved 5/consumed 7` byte-unchanged** — no partial state in the single-writer case, because D1 `batch()` is atomic: a CAS miss throws the whole batch, rolling back the earlier terminal write too. The existing "failed meter CAS" test proves the same. RESIDUAL (LOW, genuinely racy but unproven here): D1 batches are serializable per-database, so the "race between allowance read and batch" the lead posits resolves as either full-commit or full-rollback, not a split — EXCEPT the pre-batch reads (`reservation` :614, `allowance` :645) are outside the batch, so two concurrent settles can both pass the `:689 reserved >= qty` pre-check and then serialize: loser gets 409 with zero writes (safe), winner commits fully. No torn ledger demonstrated; the `void newReserved/newConsumed` dead code (:808-809) is cosmetic. Authority-loss-commits-ledger-while-task-not-terminal: refuted by construction — the ledger UPDATE carries no task-state predicate itself, but it lives in the same atomic batch whose task UPDATE carries the full guard set; if the task guard fails the batch rolls back. The REAL uncovered case is subtler: ledger CAS can SUCCEED while the task guard fails (different predicates) → whole batch rolls back → 409, safe but the supervisor cannot distinguish "retry" from "restate". No data-loss defect proven.
- **H1 largely REFUTED as specified: op-INSERT non-gating is harmless because every mutation carries guard+authorizer inline.** Static probe: claim 14 prepares, `opId` referenced 4× but in no WHERE clause; ack likewise 0 op-row-gated mutations. But the mutations don't need opId gating — each UPDATE embeds `${guard.sql} AND (${authorizer.sql})` with current-time args (claim :231/:242, ack :355, renew :453, settle :750), so a lost-authority batch writes nothing regardless of the op row. The op row is a replay/receipt record, not a lock. The fingerprint/resource check placement (AFTER batch for claim/ack/renew, BEFORE batch for settle :577-595) is the correct reading of the residual risk — which H2/H3 below measure live.
- **H2 CONFIRMED, MEDIUM: same claim key after old task terminal claims a NEW task.** LIVE: settle t1 terminal → seed t2 → same supervisor S2 reuses key K → **200 with a DIFFERENT task id**. The `principalKey = supervisor:<credential_id>` scope means even the same supervisor can double-spend one key across tasks; across supervisors (S1→S2) the key namespace differs per credential so cross-supervisor reuse is a fresh key, but within one long-lived supervisor credential the key is NOT bound to the resource. Consequence: lost-reply accounting/replay keyed by claim-key alone is ambiguous (which task did K produce?). Require: bind claim keys to task (store task_id in the op row — already stored :220-224 — and on reuse return the ORIGINAL task while its lease is current instead of electing a new one), or document claim keys as single-election-attempt tokens (replay only via the lost-claim path :287-304, which already keys on `prior.task_id` + same supervisor + unexpired — but that path only fires when NO new candidate is elected; H2 shows a new candidate IS elected and wins). Severity MEDIUM (not HIGH) because the elected task is still a legitimate queued assignment to the same supervisor — no wrong-tenant/wrong-worker execution — but the idempotency contract ("same key ⇒ same result") is violated.

- **H4 REFUTED live: simultaneous same-key different-consumption settles resolve safely.** Settle1 (5 ms) → 200 `completed`/reservation `consumed`/5 ms; settle2 same key (9 ms) → **409** (prior-fingerprint mismatch :582-594 fires BEFORE the batch). The pre-`prior`-null race (two settles same key, neither seeing a prior) serializes in D1: both carry the same key, the op INSERT is `ON CONFLICT DO NOTHING`, and the second... — precisely: both could insert-or-ignore, but the terminal-transition UPDATE is conditional on non-terminal state, so the loser finds `completed` and hits the `terminal` branch → 409 (H4's second call proves the steady state). No double-spend demonstrated.
- **H5/R2 CLARIFIED (policy revocation): claim/ack/renew/settle do NOT import `activePolicyGuard` — by design, and renew-after-revoke behavior is order-dependent.** Source fact: dispatch imports only `addQuantities/formatQuantity/isControlledMeter/parseQuantity` from hosted-entitlements; `activePolicyGuard`/`putPolicy`/`revokePolicy` appear nowhere in hosted-dispatch.ts. R2 LIVE (correct order, post-revoke): ack 200 → renew 200. H5 LIVE (reversed order: renew on `claimed` first): renew 200 (bumped fence on the claimed row!), then ack with the OLD fence → 409, then settle → 409. So revocation does NOT block renew/ack at the policy layer at all — the "settlement works after revocation" test passes because settlement deliberately tolerates policy loss (comment :517-520), but NOTHING rechecks commercial entitlement on renew: a revoked-policy supervisor keeps extending leases until deadline. Whether that is a defect depends on the intended policy model (leases as already-paid capacity vs continuous entitlement): if renew must recheck, the missing `activePolicyGuard` import is a HIGH defect; if the reservation at admission covers the full runtime, it is correct. REQUIRE the lead to rule explicitly — the code as stands implements "reserve once, renew freely", and no test pins which model is intended.
