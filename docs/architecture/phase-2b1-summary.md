## Authentication protocol and trust boundaries

`swarmforge cloud login` allocates a ten-minute transaction using a random 256-bit initiating secret held in CLI memory. The browser receives only a link ID; the CLI displays a separate 72-bit manual pairing code. The existing confidential GitHub web OAuth flow signs the browser into SwarmForge Cloud. The approval page identifies the installation, offers the user's active organizations and requires explicit code/organization approval under existing session/Origin/CSRF protection. Only the original initiating proof can poll or exchange.

Approval binds immutable account, organization, session and narrow scopes. Pending unauthenticated links are transient authorization transactions with no tenant authority; verified browser approval establishes grant ownership. Atomic D1 consumption rechecks current account/session/membership/organization, creates exactly one installation and hashed credential, and audits it. Exact-context retries return encrypted cached results only while the transaction and issued credential remain valid. Other proofs/keys cannot retrieve a grant. Polling, expiry, denial/cancellation and approval-attempt limits are enforced server-side. `cloud use <UUID>` requires fresh browser approval rather than changing an existing grant's organization.

GitHub repository credentials, website cookies, CLI bearer credentials and worker bearer credentials have separate consumers. CLI credentials have audience `cloud-cli` and scopes `identity:read`, `devices:self`; workers have audience `worker-identity` and scopes `worker:identity`, `worker:rotate`. Neither authorizes website administration, GitHub repository access or workload execution. CLI-to-cloud linking does not alter `swarmforge github login`.

Credentials have 256 random bits and are hashed in D1. CLI tokens expire after 24 hours, worker tokens after one hour; authorization grants are bounded to 30 days. Epoch rotation invalidates old general access. Only exact same-key rotation retries may recover the active successor for ten minutes, bounded by old token expiry and continuously rechecked authority. The CLI has `cloud rotate`; lost rotation results require browser reauthentication because pending rotation keys are not persisted locally.

CLI storage uses a separate private POSIX file with strict schemas, ownership/path checks, no-follow reads, exclusive temporary writes, fsync/atomic rename and private permissions. Linux/macOS file storage is implemented; OS credential vault and Windows support remain future work. The fallback protects other-user access, not same-user/root/disk compromise. Logout attempts server revocation and deletes local credentials; an unconfirmed server revoke is explicitly reported with a nonzero result. See [identity operations](../cloud/IDENTITY.md) for recovery.

## Schema and API

Migration `0002_machine_identity.sql` adds `cli_links`, `cli_installations`, `worker_enrollments`, `cloud_workers`, `machine_credentials`, `credential_rotations`, `identity_rate_limits` and an allowlisted OAuth return path. Unique constraints bind one installation/worker to one consumed transaction. Exclusive credential audience/resource checks, indexes, foreign keys and bounded expiry checks support atomic admission/rotation. Tenant/session-qualified invitation idempotency stores fingerprints and encrypted replies. No subscription tables, provider tokens or plaintext machine credentials are added.

Implemented routes and strict schemas are in [phase-2b1-api.md](phase-2b1-api.md):

- Link initiation, website metadata, initiating status, approve/deny/cancel/exchange and `/cloud/connect` browser UI.
- CLI identity, own organization choices, self-revocation/rotation, tenant device listing/revocation.
- Owner/admin worker invitations/revocation, single-use registration, worker identity/rotation, tenant worker listing/revocation.
- Existing Phase 2A account/session/organization endpoints and coarse health/readiness remain.

CLI installation `last_seen_at` is approximate, throttled to one actual write per five minutes after credential validation. It is exposed only in tenant-authorized device listing and never used for authorization. Worker enrollment creates identity metadata only; no VM, heartbeat, task, repository broker, dispatch, inference, usage or billing endpoint exists.

## Tenant authority, revocation and safeguards

Authority comes from current D1 user/membership/organization records, never requested tenant IDs, repository names, worker hints or local config. Owner/admin website sessions manage workers; ordinary active members can link their own CLI and list/revoke their own installations. Owner/admin can manage all devices in their tenant. Worker authorizers must continuously remain owner/admin. List queries/cursors/resource IDs/idempotency are tenant/principal/purpose scoped; machine and cookie audiences cannot fall through to each other.

Every authenticated request rechecks account, organization, authorizing membership, credential expiry/revocation, resource status and epoch. No cross-request authority cache exists. Privileged writes recheck authority inside the atomic D1 batch; SQL/audit failure rolls back dependent mutations. Suspension denies subsequent checks; restoring the same active authority can restore an unrevoked bounded grant. Permanent removal must revoke the installation/worker. Browser logout stops pending exchange but does not revoke already issued machine grants. Ownership changes do not transfer authorizers. Backup recovery must revoke restored sessions/machine grants and invalidate pending encrypted/signed material before reopening access.

Strict Origin/CORS, request/body limits, generated IDs, no-store/security headers, safe centralized errors and redacted route-template logging remain. Approval HTML uses nonce CSP and textContent; OAuth return targets accept only the local connect route with a UUID. No raw incoming authentication data is added to logs/audits/config output. Existing local MCP diagnostics now redact raw `sfcli_`, `sfworker_` and `sfenroll_` formats and the `credential` field even when the coordinator has never loaded a cloud account. This does not promise detection of arbitrarily encoded hostile data; no machine credentials are forwarded to worker execution, prompts, repository config or provisioning.

D1 application budgets protect OAuth starts/callbacks, links, worker identity and invalid credentials; dependency failure denies closed. Public generic denials do not allocate audit rows, and eligible failure audits are capped. Resource admission caps and per-link polling/attempt limits apply independently. These do not stop distributed quota exhaustion: edge abuse controls, quota alerts and edge CPU measurements remain rollout gates.

Cleanup runs every ten minutes, at most 500 rows per statement, preserves referenced identity and revocation history, and clears expired encrypted caches. Audits are preserved by default; optional bounded local audit pruning requires an explicit retention policy. The technical recommendation is 90 days, pending owner approval, not a configured default. [Deployment](../cloud/DEPLOYMENT.md) cites current official Workers/D1 Free limits verified 2026-10-08.

## Remaining risks and Phase 2B.2 prerequisites

1. Obtain separate authorization for remote preview resources, apply both migrations to the dedicated verified database, configure a separate preview GitHub OAuth app, and verify real browser/CLI sign-in/revocation. No production or preview deployment is automatic.
2. Measure actual edge CPU, D1 indexed reads/writes and abuse volume on the selected plan; configure edge protections and quota alerts. D1-based admission budgets themselves consume queries. Validate scheduled cleanup throughput and backup/incident recovery.
3. Decide audit/account deletion, backup retention, organization invitation/ownership transfer and membership restoration policy. Existing grant limits/admission caps are technical defaults, not pricing or paid entitlements.
4. Build the customer worker enrollment client with protected secret transport/persistence, periodic bounded rotation and revocation recovery. Current enrollment/verification APIs are working; no worker runtime claims or workload eligibility follow from them.
5. Add server-managed execution entitlements, atomic reservations, revocable task leases, scoped repository brokerage and supervisor authentication before hosted dispatch. Preserve the current distinct audiences and current membership checks; do not broaden `worker:identity` into execution authority.
6. Add installation grant reauthorization/rotation recovery UX, OS vault support and lifecycle archival as concrete needs arise. No identity/persistence redesign is needed for organization-owned billing/subscriptions later; plan claims must remain server-owned.

Stripe, subscriptions, hosted tasks, managed compute/inference and production provisioning remain outside this phase.
